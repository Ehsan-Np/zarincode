## ۱. جمع‌بندی اجرایی

۳.۳۸.۱ بخش بزرگی از حفره‌های «قابل سوءاستفاده از اینترنت» نسخهٔ ۳.۳۸.۰ را بسته است: تزریق `WP_Query`، رلهٔ ایمیل فرم تماس، جستجوی بدون allowlist، iframe ویدیوی آزاد، پیوست ZIP عمومی، نقش تیکت با `edit_posts`، و چند مورد SSRF/آپدیت.

با این حال، **یک باگ مالی Critical تازه** در همان تغییری که قرار بود M2 را درست کند ظاهر شده است: موجودی کیف پول حالا از `SUM` همهٔ ردیف‌های `completed/done` جدول `zc_transactions` خوانده می‌شود، در حالی که همان جدول دفتر **درآمد فروشگاه** هم هست. نتیجه: بعد از اولین سفارش پرداخت‌شده، موجودی کیف پول خریدار با مبلغ سفارش (و در مسیر کیف پول، دوباره با همان مبلغ) باد می‌کند؛ رزرو کیف پول هم در موجودی دیده نمی‌شود و برداشت مضاعف ممکن است.

سه یافتهٔ High باز هم روی دسترسی دوره و مدرک اثر می‌گذارند: دورهٔ رایگان برای هر کاربر واردشده باز است؛ پیشرفت درس از کلاینت جعل می‌شود و آستانهٔ ۳۰/۹۰ ثانیه یکدست نیست؛ هوک `zc_course_completed` روی هر ذخیرهٔ ۱۰۰٪ دوباره شلیک می‌شود.

| شدت | باز در ۳.۳۸.۱ | بسته‌شده نسبت به ۳.۳۸.۰ |
|---|---:|---:|
| Critical | ۱ (مالی، جدید) | ۲ (C1، C2) |
| High | ۴ | ۸ مورد قبلی + بخشی از H4 باقی است |
| Medium | حدود ۱۰ | M1، M2-قدیمی، M7، M8، H6، H8 بیشتر رفع شده |
| محصول / بدهی معماری | ۱۵+ | CPT/نقش تا حدی بهتر شده |

**حکم انتشار:** برای سایت با درگاه و کیف پول فعال، ۳.۳۸.۱ را **بدون اصلاح دفترکل کیف پول روی ترافیک واقعی نگذارید**. بقیهٔ ماژول‌های پرداخت/بکاپ/آپدیت/رزرو نسبت به ۳.۳۸.۰ قابل اتکاترند.

## ۳. امنیت — یافته‌های باز

### Critical

#### C-381. دفترکل کیف پول = درآمد فروشگاه (تورم موجودی + برداشت مضاعف)

**مسیرها**

- `inc/modules/wallet.php` → `zc_wallet_ledger_sum`, `zc_wallet_balance`
- `inc/modules/zarinpal.php` → `callback_handler` (حدود ۳۷۷) و `zc_commit_order_wallet` (حدود ۴۷۰)
- `inc/modules/gateways.php` → ثبت `type=income` / `category=order` پس از verify

**چه اتفاقی می‌افتد**

`zc_wallet_balance` بعد از وجود حتی یک ردیف `status IN ('completed','done')` دیگر به usermeta نگاه نمی‌کند و `SUM(amount)` کل جدول را برمی‌گرداند.

همان جدول برای سه چیز استفاده می‌شود:

1. واریز/برداشت واقعی کیف پول (`type=deposit|withdraw`، معمولاً `gateway=wallet|zarinpal` در شارژ)
2. درآمد سفارش از درگاه (`type=income`, `category=order`, مبلغ پرداخت‌شدهٔ **مثبت**)
3. «درآمد بخش کیف پول» هنگام commit رزرو (`zc_commit_order_wallet` دوباره `type=income` مثبت می‌نویسد)

رزرو کیف پول با `status=pending` ثبت می‌شود و از SUM خارج است، در حالی که usermeta همان لحظه کم شده. چون موجودی از ledger خوانده می‌شود، رزرو **در موجودی دیده نمی‌شود**.

**سناریوی سوءاستفاده / خسارت (بدون نفوذ خارجی)**

1. کاربر ۱۰۰٬۰۰۰ تومان شارژ می‌کند → یک ردیف `deposit` completed.
2. سفارشی ۲۰۰٬۰۰۰ تومانی را با زرین‌پال می‌پردازد → ردیف `income/order` +۲۰۰٬۰۰۰ completed.
3. `zc_wallet_balance` = ۳۰۰٬۰۰۰. کاربر می‌تواند کل مبلغ سفارش را از «کیف پول» خرج کند.
4. اگر بخشی از سفارش با کیف پول رزرو شود: برداشت `pending` موجودی را کم نمی‌کند؛ checkout دوم همان موجودی کامل را می‌بیند → **برداشت مضاعف** تا وقتی ردیف‌ها completed شوند.
5. پس از پرداخت موفق، `zc_commit_order_wallet` یک `income` مثبت دیگر به اندازهٔ بخش کیف پول می‌نویسد. حتی اگر برداشت بعداً completed شود، `−X + X` همدیگر را خنثی می‌کنند و درآمد درگاه همچنان روی کیف پول خریدار می‌ماند.

**رفع پیشنهادی (پیاده نشده)**

- موجودی = `SUM` فقط ردیف‌هایی که واقعاً کیف پول‌اند: `type IN ('deposit','withdraw')` یا `category IN ('charge','purchase','cashback',…)` و **هرگز** `type=income`.
- درآمد فروشگاه را در جدول/دستهٔ جدا نگه دارید، یا `user_id=0` برای درآمد فروشنده.
- رزرو باید در SUM بیاید (`pending` را هم حساب کنید) یا از ابتدا `completed` باشد و restore آن را reverse کند.
- پس از اصلاح، یک مهاجرت یک‌بارمصرف موجودی‌های بادکرده را از روی usermeta یا تفاضل income بازسازی کند.

### High

#### H-381. دورهٔ رایگان = دسترسی همهٔ کاربران واردشده

`inc/modules/course.php` → `zc_user_has_course`

```php
$price = (float) get_post_meta( $course_id, '_zc_price', true );
if ( $price <= 0 ) {
    return true;
}
if ( zc_user_has_subscription( $user_id ) ) {
    return true;
}
```

- هر کاربر لاگین‌شده به **همه** دوره‌های با قیمت ۰ یا خالی دسترسی کلاس درس، آزمون، تمرین و پیشرفت دارد؛ ردیف `zc_enrollments` لازم نیست.
- `zc_ajax_free_enroll` ثبت‌نام می‌سازد ولی گیت دسترسی آن را دور می‌زند.
- اشتراک فعال (`zc_subscription_is_active` یا متای قدیمی `zc_subscription_expire`) **همه** دوره‌های پولی را باز می‌کند؛ محدود به پلن/کاتالوگ نیست.

اگر محصول «پیش‌نمایش رایگان فقط با ثبت‌نام» یا «اشتراک فقط دستهٔ X» باشد، این یک باگ دسترسی است نه تنظیمات.

**رفع:** رایگان فقط با enrollment (یا فلگ صریح `_zc_open_enroll`). اشتراک فقط دوره‌هایی که پلن اجازه می‌دهد.

#### H-382. پیشرفت درس جعل‌پذیر و آستانه‌ها ناسازگار

| مسیر | وجود جلسه | حداقل بدون duration | هوک تکمیل |
|---|---|---|---|
| `zc_ajax_save_watch` | `zc_find_lesson` الزامی | ۹۰ ثانیه | هر بار ۱۰۰٪ |
| `zc_rest_progress_post` | **بررسی نمی‌شود** | ۹۰ ثانیه | هر بار ۱۰۰٪ |
| `zc_ajax_complete_lesson` | **بررسی نمی‌شود** | **۳۰ ثانیه** | اگر `zc_save_lesson_progress` باشد، همان هوک |

کلاینت `seconds` و `duration` را می‌فرستد. اگر `duration` را ۱ بگذارد و `seconds` را ۱، با آستانهٔ ۸۰٪ درس completed می‌شود. برای iframe، مسیر قدیمی `complete_lesson` هنوز با ۳۰ ثانیه کافی است.

`zc_save_lesson_progress` هر بار که پیشرفت ۱۰۰٪ است و status=completed باشد `do_action('zc_course_completed')` می‌زند. این هوک گواهی، وب‌هوک خروجی و اعلان را دوباره اجرا می‌کند.

**رفع:** duration را از متای درس بخوانید نه از POST؛ یک آستانه؛ `zc_find_lesson` در هر سه مسیر؛ هوک تکمیل فقط بار اول (فلگ usermeta یا ستون).

#### H-383. کلید API کاوه‌نگار همچنان در path

`inc/modules/sms-kavenegar.php` خط ۶۴:

`https://api.kavenegar.com/v1/{APIKEY}/...`

فیلتر `zc_kavenegar_endpoint` برای پروکسی هست، ولی پیش‌فرض کلید را در access log، CDN و Referer می‌گذارد. در ۳.۳۸.۱ عمداً طبق API رسمی باقی مانده؛ از نظر عملیاتی همچنان High است.

#### H-384. توکن ربات تلگرام/بله در URL

`inc/modules/messenger-bot.php` → `zc_messenger_request`

`sprintf( $config['api'], $token, $method )` → `https://api.telegram.org/bot{TOKEN}/sendMessage`

مشابه H-383. برای بله، secret وب‌هوک هم با `add_query_arg('secret', …)` روی URL ثبت می‌شود (لاگ وب‌سرور).

### آنچه درست پیاده شده (تعادل)

- نانس سراسری `zc_check_ajax` روی اکشن‌های فرانت.
- `GET_LOCK` روی تغییر کیف پول، صف اعلان، ظرفیت رزرو.
- Idempotency `ref_id + category + gateway` در `zc_add_transaction`.
- کال‌بک شارژ کیف پول: کاربر جاری باید با `pending.user_id` یکی باشد.
- کال‌بک زرین‌پال: `hash_equals` روی authority ذخیره‌شدهٔ سفارش.
- آزمون: state سرور، توکن یک‌بارمصرف، محدودیت تلاش دوره.
- لایسنس پلتفرم (در صورت فعال): HMAC + پنجرهٔ زمانی (از حسابرسی قبلی؛ در این دور دوباره خط‌به‌خط باز نشده).
- هدرهای nosniff / SAMEORIGIN / Referrer-Policy / HSTS / CSP حداقلی.
- بکاپ AES با کلید جدا از `AUTH_KEY`.
- آپلود تیکت: MIME/پسوند + پوشهٔ Deny + پروکسی مالکیت.
- وب‌هوک ربات بدون secret → ۴۰۳ و `hash_equals`.
- XML-RPC پیش‌فرض خاموش.

## ۷. اولویت اقدام پیشنهادی

### قبل از هر سایت با پرداخت واقعی

1. **C-381** جدا کردن دفتر کیف پول از درآمد سفارش؛ شامل رزرو pending در موجودی؛ مهاجرت موجودی‌های خراب.
2. یکسان‌سازی و سخت‌کردن پیشرفت درس (H-382) اگر مدرک/وب‌هوک تکمیل به پول یا اعتبار گره خورده.
3. تصمیم محصول روی دورهٔ رایگان و اشتراک همه‌دوره (H-381) و اعمال در `zc_user_has_course`.

### اسپرینت بعد

4. کلید کاوه‌نگار و توکن ربات از URL خارج شود (پروکسی یا header اگر API اجازه دهد).
5. کد اتصال ربات ۱۲+ نویسه + TTL اجباری در `zc_get_connect_code`.
6. secret بله فقط هدر، نه query.
7. هوک `zc_course_completed` یک‌بارمصرف.
8. پنل مدرس واقعی یا حداقل عدم ادعای «کمیسیون» روی `SUM(enroll.price)`.
9. ویدیوی امضاشده برای دورهٔ پولی.

### بدهی ۴.x

10. انتقال wallet / enrollment / licenses / REST / OTP به Zarincode Core.
11. REST اپ با توکن.
12. تست واحد: ledger، callback زرین‌پال، رزرو کیف پول، enrollment، OTP.
13. دفترکل دوطرفهٔ حسابداری جدا از کیف کاربر.
